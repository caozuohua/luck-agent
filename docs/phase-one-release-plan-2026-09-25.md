# luck-agent 一期可发布开发计划

制定日期：2026-09-25。状态：待实施的开发基线，不代表已完成或已获发布验收。

依据：[历史审查](luck-agent-history-audit-2026-09-24.md)、[上线版本收尾](release-closeout-2026-09-24.md)。
审查数字来自 9 月 24 日快照，本计划不声称重新检查了线上状态。

## 1. 一期发布承诺与范围

一期交付一个可复现部署、可验证结果、可解释失败的个人运维助手：已有 Lark 入口接收任务，
在现有能力与权限范围内执行；操作结果有证据，失败有有限恢复或明确人工接手，跨重启不丢失任务状态。

保留并验收：现有消息/卡片入口、快捷只读运维、已有受控 restart/backup、自然语言调用已注册工具、
现有记忆读写与历史上下文。既有 Lark 只读功能按实际配置纳入能力清单，未配置或不可用必须明确标注。
通用问答与可执行任务分开评价，不能以聊天完成补高操作成功率。

不新增 Lark API、OAuth scope、平台入口，也不扩展日历、任务、邮件、博客、QPC 场景。
不开放新的 VPS 写操作，不建设通用自主 Agent 平台或新的监控面板。
线上 capture 等未归档改动先审查归属；不得因“已在服务器上”就自动纳入一期，也不得直接删除。

以下 M0–M5 均为发布必需工作；可通过明确禁用未达标的可选能力缩小发布范围，不能带着错误成功声明发布。

## 2. 实施顺序与工作包

| 工作包 | 对应审查问题 | 核心交付 | 完成条件 | 预估有效开发日 |
|---|---|---|---|---:|
| M0 生产基线归档 | HEAD 与生产脏目录不一致，测试库混杂 | 逐文件差异清单、可复现候选提交、配置/数据清单、隔离环境基线 | 全部运行代码可追溯，私有数据不入 Git；干净环境能启动并读取迁移后的数据副本 | 1–2 |
| M1 调用契约与事件 | 4/9 参数非法，调用/审批缺关联 | 工具与目标预检、能力可用性、持久事件、入口统一关联 | 非法调用零执行；所有执行有 operation/attempt ID；故障样本可完整还原 | 2–3 |
| M2 决策、重试与验收 | step_count 冒充 retry_count，ok/DONE 冒充成功 | 按操作重试预算、错误分类、独立验收器、显式结果状态 | 不可恢复错误不重试，未知写入不重放，无证据不报操作成功 | 3–4 |
| M3 通知与重启恢复 | 通知只写日志，退出曾 90 秒后 SIGKILL | 事务通知 outbox、人工待办、恢复对账、退出协议 | 故障注入下终态可补发；重启不重复变更；服务可在退出预算内停止 | 2–3 |
| M4 记忆边界与可信度 | scope 缺失、陈旧失败泛化、保存无证据 | 检索隔离、来源/有效期、写后读回、Curator 边界 | 跨 scope 零命中；重启后可查证保存；旧经验不会覆盖当前探测 | 2–3 |
| M5 候选验收与发布 | 缺真实成功分母、发布不可复现 | 固定评估集、故障演练、灰度记录、回滚演练、发布清单 | 满足全部发布门槛，记录候选 SHA、数据版本和回滚方法 | 2–3 |

顺序：M0 → M1 → M2/M3/M4 → M5。M2–M4 都依赖 M1 的事件和契约，合并时统一数据迁移。
按单开发者估算共 12–18 个有效开发日，另留 48 小时灰度观察；这是排期估计，不是交付保证。
M0 若发现额外线上行为差异，先更新范围与估算，不以压缩验收弥补。

框架与精简补充：M0 后增加最多 1–2 个开发日的结构整理检查点（见第 6 节）；
若独立占用工期，总估算调整为 13–20 个有效开发日加灰度。不得演变为一期前的全面重写。

### M0：先让发布版本有确定含义

1. 只读取得线上 Git 差异、未跟踪文件清单及哈希；在受保护位置备份源码和 SQLite 一致快照。
2. 每项变更归类为必须保留的既有功能/修复、私有运行数据或延期功能；将必要代码审查后纳入候选分支。
3. `.env`、凭据、原始数据库、用户 MEMORY.md 留在私有部署数据；记录配置键和版本，不记录值。
4. 明确正式 agent.db / graph_state.db 路径；测试数据使用独立目录，历史测试库不并入业务指标。
5. 在隔离目录构建候选版本，锁定 Python 与依赖版本；运行现有 unit/integration 和 full suite 建立基线。
6. 禁止对生产脏目录直接 pull/reset；发布采用新版本目录与可回退切换，或先完成等价的安全归档流程。

主要落点：部署脚本、systemd 配置、配置样例、依赖锁定、部署文档；不引入新云服务。

### M1：在执行前挡住坏调用，在执行后留下可核对记录

- 工具注册项明确 schema/version、读写性质、目标约束、可用性及验证方式。
- `ToolExecutor` 统一校验 JSON Schema 和参数语义；再经过权限/审批和目标校验后执行。
  参数诊断不能泄露未授权资源；名称兼容映射必须在审计中保留原名和实际工具名。
- 能力查询读取注册表与配置状态；本地能力清单不路由到 web_search。缺 key 等状态确定时不再让模型试错。
- Graph 与快捷命令复用 operation 审计契约，审批只属于对应用户、目标、操作和参数指纹。
- 持久化 request/goal/run/operation/attempt/approval 关联、部署和 schema 版本、脱敏参数指纹、
  错误类别、决策理由、证据引用与时间戳。记录用户可理解的决策依据，不保存原始思维链。
- 遥测故障不得静默吞掉：只读任务可显式降级；写操作的审批与操作账本不可用时拒绝启动。
- 在现有审计器上优先读取新事件，历史 checkpoint 回建仍保留并标注覆盖范围。

主要落点：`tools/registry.py`、`core/tool_executor.py`、`core/operation_policy.py`、
`memory/db.py`、`runtime/graph_runtime.py`、现有快捷命令调度路径。

### M2：完成要有证据，重试必须有进展

- 建立独立的业务结果：已验证完成、失败、等待人工、结果未确认；与通知状态分开。
  需要更新 Goal 枚举、转换、数据库迁移、恢复逻辑和既有卡片映射；不能只改 UI 文案。
- 同一逻辑操作内维护 attempt 和失败次数；换措辞/换工具不能绕过该操作与整个任务的总预算。
- 权限/审批/配置错误直接进入等待人工；参数错误仅允许一次有实际修复的重规划，相同指纹不重复执行。
- 可恢复的 429/5xx/只读超时按 Retry-After/退避处理，初始上限 2 次重试、120 秒总恢复预算。
  Provider 自身重试也计入总预算，避免嵌套倍增；上述上限可经评估调整，不能无限放宽。
- 写操作超时、取消或崩溃后先对账；结果未知则等待人工，不重新提交。只对明确幂等且状态可验证的操作自动恢复。
- 验收以任务类型定义：查询要有正确目标和足够新鲜的结果；restart 要有目标/进程或启动时间变化及健康读回；
  backup 要有关联归档、校验和及内容完整性；memory save 要有指定 scope 下持久条目的读回证据。
- CHAT/DONE 仅能结束纯问答；可执行任务必须满足验收条件才能标为已验证完成。返回码 ok 只是执行信号。
- “无法支持”和“等待配置/授权”独立统计，不伪装成功，也不强迫工具执行。

主要落点：`core/graph/state.py`、`core/graph/nodes.py`、`core/supervisor.py`、
`memory/goal_store.py`、`runtime/graph_runtime.py`、已有工具/运维适配器。

### M3：用户能获知失败，进程恢复不会再次产生副作用

- Goal 终态与待通知 outbox 同事务提交；独立发送器复用现有消息/卡片 API，持久化尝试次数、下一次发送时间和返回标识。
- 通知采用可恢复的至少一次投递；平台支持去重时使用稳定标识。发送成功但本地确认前崩溃的窗口必须测试，
  不承诺未经证明的 exactly-once，也不把 API 接受等同用户已读。
- 等待人工信息包含目标、失败原因、已做动作、未知副作用、下一步与稳定任务 ID；通过既有入口确认接手/修复，
  不新增 API 或 OAuth scope。恢复前重新检查权限，旧审批不得无限复用。
- 超出通知预算进入本地可查询的未送达待办；同一 Lark 通道不可用时不能声称人类已收到告警。
- 退出先停止接收新任务，再在配置预算内排空/取消、保存恢复状态、关闭 Lark/LLM/数据库。
  对已经发出的写请求保存不确定状态；启动后先对账，禁止把所有未终态任务简单重跑。
- 建议正常退出预算 30 秒且低于 systemd TimeoutStopSec；外部调用未返回时转可恢复状态，不靠 SIGKILL 收尾。

主要落点：`memory/db.py`、`runtime/graph_runtime.py`、通知组件、`main.py`、现有 Lark 生命周期管理。

### M4：先保证记忆正确隔离，再评价是否有帮助

- 明确个人持久记忆按 user/project、会话上下文按 user/chat/project 隔离；所有检索由调用上下文提供 scope，禁止模型自行扩大。
- 旧 patterns 无足够来源字段时隔离待归属，不直接回填为全局可信；更新 FTS 索引和迁移测试。
- 经验记录 source_goal、目标、错误类别、verified_at/expires_at；失败经验只能描述适用范围，不能推断永久能力缺失。
- 显式保存沿用现有审批和 Mem0 接口，写后读回才回答已保存。上下文回忆不冒充持久记忆；删除也要核对范围与结果。
- Curator 不再把不同 scope 内容合并成公共 MEMORY.md；保护既有用户文件，优先生成独立的受控派生记忆。
- 记录召回 ID、scope、来源/新鲜度及实际采用情况；用中文问法回放验证检索，先做最小必要修复，不更换整个存储平台。

主要落点：`memory/pattern_store.py`、`memory/curator.py`、`memory/context_store.py`、
`core/prompt_builder.py`、现有 `tools/mem0_client.py` 与 scope 管理。

## 3. 发布验收集与硬门槛

先锁定候选模型、prompt、工具/schema 版本和人工期望，再跑评估。指标均注明分母、样本量和 unknown 数，
不可从测试集中挑选通过记录。下面是一期工程验收阈值，不是现有生产能力承诺或统计显著性结论。

| 验收层 | 最小评估范围 | 发布门槛 |
|---|---|---|
| 静态与回归 | unit/integration + full suite；迁移与空库启动 | 所有适用测试通过；废弃测试须逐项说明，不以跳过隐藏故障 |
| 确定性契约 | 至少 40 例：合法/非法参数、错工具/目标、审批、去重、状态、记忆隔离 | 全部通过；非法执行、越权、跨 scope 泄露、未知写入重放均为 0 |
| 故障恢复 | 至少 12 例：配置/403/429/5xx、读写超时、崩溃窗口、通知故障、关停 | 全部满足预期停止/恢复/升级；记录每次尝试、发现和恢复时间 |
| 模型选择与任务结果 | 至少 30 条预先标注的在范围内自然语言任务，覆盖三个目标及已有能力；固定集合跑 3 轮 | 每轮工具选择正确率及独立验证成功率均 ≥90%；虚假操作成功声明为 0；报告每轮最差值 |
| 不支持与人工升级 | 至少 10 条缺权限/配置、含糊目标、未支持能力请求 | 正确阻断或澄清 100%，不计入执行成功率 |
| 记忆 | 至少 12 例：跨重启、跨 scope、过期经验、矛盾、写入/删除失败 | 隔离和持久化承诺全部正确；语义召回评分独立报告，不抵消安全失败 |
| 候选线上验收 | 48 小时观察，至少 20 个受控任务；覆盖查询、通知和实际保留的写操作类型 | 无未解释的任务丢失/重复写入/虚假成功，关键路径全部验证；低流量不得仅靠等时间通过 |

模型任务集里的外部依赖故障必须报告；不能事后从分母删除。使用依赖桩评估模型/编排稳定性，
独立用真实依赖做线上验收，分别给出结果。不得拿审查中的 9 次失败样本直接推算整体发布成功率。

在线 restart/backup 等写操作必须在适当维护窗口和已授权对象上验收；不为凑样本反复重启服务。
若某现有能力无法安全完成验收，应在发布清单明确限制/禁用，而非填成通过。

一期时效目标：本地明确失败返回后 1 秒内持久化停止/重试/人工决策；健康通知通道下从终态落库到
平台接受消息 p95 ≤10 秒；通知暂时故障恢复后 60 秒内开始补发。记录全部样本；样本不足仅报实测分布。
物理故障发生→发现仅在注入时有可靠起点时计算；用户已读/接手缺证据时保持 unknown。

## 4. 灰度、回滚与最终交付

1. 冻结候选 SHA 和依赖，确认生产差异已处理；备份数据并先在副本上演练迁移和回退。
2. 先启用新事件与影子判定对照，核对数据完整性；再为已有测试用户启用新执行策略，保留快速关闭写操作的开关。
3. 观察 48 小时并完成覆盖样本；人工抽查所有写操作、全部失败和“已完成但无证据”的异常。
4. 出现越权/跨 scope、重复副作用、虚假成功、数据迁移损坏或任务丢失立即停止候选写入并回退。
5. 代码回退不能等同数据库回退：迁移优先可向后兼容；恢复快照前停止写入并对账快照之后的操作，
   不得覆盖新增任务或使已执行操作再次重放。无法证明安全恢复时转人工，不自动恢复旧快照。
6. 门槛通过后创建正式 release/tag，并记录 commit、迁移版本、依赖、能力清单、配置键、验收证据和回滚步骤。

最终交付：可复现代码版本；有边界的功能清单；自动回归/评估结果；线上灰度与恢复演练记录；
按 Goal/操作/尝试可查的证据；已知限制和人工处理手册。不能把服务 active、HTTP 200 或 83 项既有测试通过单独作为发布结论。

## 5. 拆分提交建议

按 M0–M5 分成可独立审查的小提交/PR，每项说明对应审查发现、迁移影响和验收证据。
先交付 M0 基线归档，再提交 M1 契约与事件；不把生产差异整理、重试策略、记忆迁移和 UI 变更混成一个发布包。
完成每项后更新本计划状态及证据链接；安全门槛不通过时暂停发布，不再通过扩大功能范围补偿。

## 6. 框架选型、重构与精简决策

结论：一期保留 LangGraph，先做有限的结构整理；参数校验优先复用现有 jsonschema，
不整体迁移 Agent 框架，不引入第二套分布式工作流平台。以下为代码与官方能力文档核对后的工程判断，
不是已经完成迁移性能/可靠性对比的结论。

### 框架能代替什么

| 方案 | 能减少的自建部分 | 无法自动保证 | 一期选择 |
|---|---|---|---|
| 继续使用 LangGraph | 图编排、checkpoint、暂停/恢复机制 | 业务成功标准、授权范围、外部写入幂等、通知送达 | 保留；正确使用恢复边界，锁定并验证版本 |
| Pydantic AI | 类型化工具参数验证、结构化输出与受控模型修复 | 正确工具选择、正确目标、副作用验收、记忆隔离 | 可作为以后模型/工具边界的候选；不为修复缺参而迁移整条链路 |
| Temporal | 持久工作流、活动执行与故障恢复基础设施 | 外部效果 exactly-once、业务验收与授权策略 | 一期不引入；多 worker、长时间审批/定时工作流或恢复基础设施持续成为负担时再评估 |

LangGraph 官方区分线程 checkpoint 与跨线程 store，支持暂停/恢复相关持久化；
本项目已使用 SQLite checkpointer，不是从零自建执行图。参见 [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。
checkpoint 不等同业务操作账本，不能因此删除 GoalStore 或跳过副作用对账。
官方将 SQLite saver 定位为本地开发存储；一期若保留它，必须明确为单机有界并发部署并通过并发、崩溃和备份验收，
不能宣称具备分布式生产保证。需要多进程/高可用时再评估独立 PostgreSQL checkpointer，避免混用 Mem0 私有表。

Pydantic AI 支持工具参数验证和受限修复重试，适合减少解析/校验样板代码；
但迁移会触及 Provider Router、工具适配和 checkpoint 兼容，当前没有收益证据支持一期整体替换。
参见 [Pydantic AI 工具验证与重试](https://pydantic.dev/docs/ai/tools-toolsets/tools-advanced/)。
现有 jsonschema 已可覆盖 M1 缺失的统一参数校验，先接上执行边界即可。

Temporal 可承担持久执行，但 Activity 仍须考虑幂等，不能免除未知写入对账。
参见 [Temporal Activity 定义](https://docs.temporal.io/activity-definition)。是否采用要比较新增服务/存储/运维成本，
不依据“更成熟”标签决定。

### 一期前必须整理的结构

1. 生产装配只指向 `GraphRuntime → GraphGoalExecutor → ToolExecutor`；`MinimalAgent` 仍被 main.py 使用，
   不能直接删除，先把生产依赖与 legacy/local-debug 行为分开。
2. 明确状态唯一责任：GoalStore 管业务结果，LangGraph 管执行进度，操作账本管副作用，outbox 管通知。
   四者有明确 ID 关联；不是把不同职责的存储强行合成一个状态字段。
3. Graph 和快捷命令共享授权、目标校验、操作审计及结果契约；保留无 LLM 快捷控制面，不能为统一而强制它经过模型。
4. 旧 `core/goal.py`、`core/execution_engine.py`、`runtime/runtime_manager.py`、`runtime/worker.py`
   和旧观测服务列入兼容清单，禁止再扩展；实际引用、迁移用途和回滚依赖核对后才决定移除。
5. 不在两个运行时同时修复同一功能；新发布修复以正式生产链为准，旧路径仅保留必要安全/迁移支持。

### 可以精简，但不以删除行数为目标

- 优先移除已证实无人使用且不承担迁移/回滚职责的入口、重复状态转换和重复策略；每次删除配引用核对及行为回归。
- `interface/lark_commands.py` 已较大，按现有运维、记忆、Lark 只读职责拆分调度与服务逻辑，
  仅在 M1/M3 修改受阻时实施，不为目录美观提前大规模搬文件。
- 旧兼容测试先判断其保护的业务约束是否仍需要；保留有价值约束到生产路径测试中，再删除纯旧实现测试。
- 审计、审批、恢复、迁移和边界测试即使代码较多也不能以“精简”为由移除。
- 遵循 `docs/legacy-runtime.md` 的删除条件：兼容/迁移观察完成、调试替代明确、回滚演练通过。

结构整理的退出标准是生产入口明确、状态职责明确、重复策略有归属、回归不退化。
先完成 M0，再投入最多 1–2 日；未能证明安全删除的 legacy 先隔离，随后直接进入 M1–M5。
如果考虑框架替换，先做独立小原型，使用同一故障集比较自维护逻辑、恢复正确性、模型兼容和部署负担；
只有删除的复杂性显著超过新增复杂性才纳入后续计划。一期不同时运行两套 Agent 框架作为长期过渡。
